# Windows 真实输入验证（2026-11-11）

本次补齐真实 Windows 鼠标、键盘和当前中文拼音输入法候选窗验证。测试使用仓库构建的 release、独立 APPDATA/LOCALAPPDATA、关闭自动保存和更新的临时配置，以及 `target/tmp` 中的专用文档。没有修改使用者的日常配置或文档。

## 自动化接口恢复

`CODEX_CLI_PATH` 原先指向 `.../Codex/bin` 目录，启动该目录能稳定复现 Windows 原生错误 5；改为同目录的 `codex.exe` 后启动探针正常。用户重启 Codex 后，两个官方计算机控制入口均恢复。未修改 ACL、安全、隐私或锁屏策略。后续锁屏由用户解锁；窗口提供的 `Raise` 动作恢复了测试窗口焦点。

诊断记录：[windows-computer-use-recovery-2026-11-11.json](windows-computer-use-recovery-2026-11-11.json)。

## 实机发现与修复

1. **中文提交后撤销恢复了临时拼音。** 真实按键 `n i h a o` 显示系统候选窗，停顿后空格提交“你好”，旧版 Undo 重新出现 `ni hao`。普通输入的 900 ms 合并超时错误地分割了仍在进行的 IME 会话。修复后 IME 以提交、取消和显式编辑边界结束捕获，普通输入超时保持原样。修复版候选选择停顿约 4.15 秒后，Undo 恢复原文，Redo 恢复“你好”，Escape 不残留拼音。
2. **清空表格矩形选区时视口跳动。** 已显示的表格因内容变化失去测量值，被预布局光标定位误认为屏幕外的新行。现在仅在源码归属和已显示范围均可验证时等待新单元格几何，再按实际溢出量微调。屏幕外和新建行继续使用原有定位路径。
3. **代码块 Copy 按钮跳到左侧。** 隐藏语言编辑芯片后，单独的 Copy 子元素失去了两端对齐的占位。自动左边距使其保持在右侧。

撤销快照仍不持有派生缓存；没有新增文档级缓存、依赖或每键完整解析。

## 真实输入覆盖

官方计算机控制接口发送 OS 输入；候选窗是实际输入法弹窗。未用应用回调替代这些步骤。

| 场景 | 观察和校验 |
| --- | --- |
| 拼音输入 | 真实候选窗显示“你好”，位置随光标移动；延迟提交、一次 Undo/Redo、Escape 取消 |
| 可视化文本 | 双击、鼠标拖选、删除和一次撤销 |
| 列表子树 | 从父列表手柄拖到末尾兄弟之后，子项和嵌套围栏代码一同移动；保存后核对源码，再一次撤销并逐字核对原文 |
| 表格 | 鼠标跨单元格矩形选择、清空、Undo；末格 Tab 新增一行并可撤销。修复后的清空与撤销均保持视口位置，保存源码与原始 fixture 完全一致 |
| 代码 | 实际点击折叠控件通过；语言芯片显示和隐藏时 Copy 均保持右侧位置 |
| 大文档 | 1 MiB 混合 Markdown 中持续发送独立按键，核对保存文本；中文候选窗、滚轮和视口底部组合输入取消 |

## 回归与测量口径

新增两项 IME 候选停顿回归和一项表格视口回归，均先观察失败再修复。最终根包桌面测试 **788 通过、2 个既有忽略项、0 失败**，帧请求合约的根包集成测试 **3 通过**（与独立运行的三项合约测试为同一组，不重复计数）。格式检查、`git diff --check` 和变更规范校验通过。

`Invoke-FluentEditingSmoke.ps1` 仍是原生窗口中的应用回调回放，本次增加候选停顿和表格视口断言。它与上面的 OS 输入测试分别记录，不能将回放本身解释为系统候选窗验证。

输入时间从应用收到输入回调计算到当前版本光标 paint；打开时间从应用读取文档计算到正文 paint。两者不包括完整 OS 输入传输或 GPU 呈现。RSS/Private 来自独立测试进程，不包含构建进程；显存未单独测量。

首次定位阶段的 360 次连续按键保存文本逐字符一致，1 MiB 打开到正文 paint 为 129.06 ms，输入 P50/P95 为 39.83/46.19 ms。后续使用记录了无编译进程的新实例复测，并保留每个阶段的全部样本。

修复 IME、表格视口与 Copy 布局的 release SHA-256 为 `C6FB42C23ED2F9CA2D2B26BFADA201EBF928328BE4F475A9AFB41947A9E0A158`。用户再次解锁后，上述三项修复的实际 Windows 验证通过。共核对 1080 次独立 OS 按键后的完整文件，及英文撤销、批量文字输入后的完整文件，均与预期逐字一致。这些是官方工具发送的系统事件，不是人工硬件按键延迟基准。

同一构建曾有两次回调回放在锁屏期间的剪贴板环节失败：`OpenClipboard` 在现有 75 ms 有界重试后返回 `0x80070005`。解锁后未改动代码、权限或重试时间，重新回放全部通过，包括新增表格视口及 IME 停顿断言。通过记录见 [原生回放原始数据](fluent-editing-native-replay-pre-frame-2026-11-11.json)。Windows 剪贴板是互斥资源，参见 [Microsoft 的说明](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-operations)；失败当时的具体占用者没有证实。

## 连续输入发现的尾延迟

帧调度修复前，同一 1 MiB 文档从文件读取到正文 paint 为 **146.36 ms**。无编译进程时连续按键的实测如下；附加复测部分时段还采集了进程 CPU，因此不能将三行视为完全相同负载。

| 阶段 | 按键数 | 输入 P50 ms | 输入 P95 ms | 最大值 ms | RSS MiB | Private MiB |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 第一轮 | 360 | 41.22 | 47.13 | 91.10 | 270.79 | 229.66 |
| 第二轮 | 360 | 41.55 | 74.50 | 300.46 | 275.91 | 234.61 |
| 附加诊断复测 | 360 | 89.26 | 185.95 | 417.93 | 312.07 | 268.86 |

返回小文档后 RSS/Private 回落到 **202.12/157.46 MiB**，大文档缓存能够释放。[原始 OS 输入数据](fluent-editing-windows-os-input-2026-11-11.json)保留了全部延迟样本和内存计数，未删除峰值。

这些峰值没有被判为“完全不卡顿”通过。Windows 系统性能记录被策略拒绝（`0xc5585011`），因此增加现有按需诊断开关下的编辑、渲染开始、模型就绪和光标绘制分段计时，以及 UI 线程 CPU 计时；普通运行不采样。

诊断构建在额外 180 次独立输入中复现 P95 **391.38 ms**、最大 **832.74 ms**。最大样本中，编辑完成为 1.22 ms，渲染开始为 797.28 ms，且这段等待 UI 线程 CPU 计数没有增加；模型就绪为 827.64 ms，光标 paint 为 832.74 ms。本机 CPU 计数约以 15.625 ms 跳变，短阶段的零值表示没有可分辨的 CPU 增量。[分段原始数据](fluent-editing-input-frame-before-2026-11-11.json)支持将主要等待定位到渲染调度之前。

Windows 后端原先依赖 vsync 无效化后低优先级 `WM_PAINT` 触发绘制；[Microsoft 的消息调度顺序](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getmessage)说明已投递消息和输入先于 `WM_PAINT`。已实现可合并的输入后帧消息，输入回调结束后在 UI 线程处理，保留原有 dirty 检查及常规 paint/vsync 路径。每窗最多一个待处理请求，无新增后台线程或轮询。合并、投递失败恢复和绘制期间再请求的三项测试通过。
