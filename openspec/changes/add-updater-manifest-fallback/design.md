# Design: add-updater-manifest-fallback

## Context

Since `add-signed-one-click-updates`, the Windows signed updater reads its manifest from one hardcoded URL. Commit `b5da3a9` moved that URL to the Aliyun OSS mirror after a real client failed with "checking the signed update manifest" on a network that reaches `api.github.com` but not GitHub's release-asset CDN. That single-host fix leaves the updater dependent on one CDN with no recovery path when OSS itself is unreachable.

`cargo-packager-updater` 0.2.3 (read from the vendored crate source) already supports an endpoint list: `Config.endpoints` is a `Vec<Url>`, and `check()` tries each endpoint in order, keeping the first successful release. A network error (`request.send()` failure) or a non-success status falls through to the next endpoint; the last error is returned only when every endpoint failed. The installer URL is taken from whichever manifest succeeded, and the minisign signature embedded in that manifest is verified against the public key baked into the binary.

The release pipeline has two publication targets for `update.json`: the GitHub Release (uploaded by the `release` job) and the OSS `latest/` prefix (uploaded by the `mirror-oss` job). Today both receive the same file, whose installer URL points at OSS (generated by the `prepare-update` job's "Build update.json" step from `OSS_PUBLIC_BASE`/`OSS_PREFIX`).

## Goals / Non-Goals

**Goals:**

- A Windows client that cannot reach one manifest host automatically gets the manifest (and its installer) from the other.
- Each distribution host serves a self-consistent pair: a manifest whose installer URL lives on the same host, so a fallback path never crosses back to the host that just failed.
- No third-party region lookup, no new user-facing strings, no change to the version check, signature scheme, or manual-download fallback.

**Non-Goals:**

- Geo-IP / locale-based endpoint selection (rejected; see Decisions).
- Changes to the initial `api.github.com` latest-release version check.
- Linux or macOS automatic updates.
- Updater key rotation or Authenticode signing.
- New installer formats for any platform.

## Decisions

### Ordered endpoint list: OSS first, GitHub second

`install_signed_update` passes `endpoints: vec![OSS_MANIFEST_URL, GITHUB_MANIFEST_URL]` instead of a single URL. Alternative considered and rejected: geo-IP region detection — it adds a third-party dependency, sends the user's IP to an extra service, misclassifies VPN/travel users, and measures registration origin rather than actual reachability; endpoint order plus fallback routes by what the client can actually reach. A latency race between hosts was also rejected because the crate probes sequentially and a custom client would mean reimplementing the updater.

Order rationale: Markion's distribution infrastructure (the OSS mirror itself) exists for mainland users, and GitHub-first would make every mainland update check pay a slow failure first — the crate sets no request timeout, and a blackhoiled TLS handshake can stall for minutes; connection resets typically cost a few seconds. OSS-first costs overseas clients a successful fetch from a cross-border host (slower but working), and they still get GitHub if OSS is unreachable.

### Two manifest variants with per-host installer URLs

The `prepare-update` job generates the updater manifest that the GitHub Release attaches, naming the GitHub asset URL (`https://github.com/willmove/markion/releases/download/vX.Y.Z/<installer>`) as the installer download. The `mirror-oss` job derives the OSS variant by rewriting only that URL to the OSS object (`${OSS_PUBLIC_BASE}/${OSS_PREFIX}/latest/<installer>`) before uploading — in tag mode from the build artifact and in mirror-repair mode from the manifest downloaded off the published Release. Deriving one variant from the other guarantees the shared metadata (`version`, `pub_date`, `format: "nsis"`, byte-identical `signature`) never drifts, because the minisign signature covers the installer file, which is identical on both hosts.

Alternative considered and rejected: keep a single manifest (OSS URL everywhere) and only fall back for the manifest fetch — a client that fell back to GitHub because OSS was unreachable would then be told to download the installer from the host that just failed. Per-host variants keep every successful path single-host.

### Trust posture unchanged

`update.json` itself is not authenticated by the crate; the minisign signature (verified with the embedded public key) covers the installer. Both hosts serve pipeline-generated output, and a tampered manifest can at worst point the client at a payload that fails signature verification — a denial of service, not an execution vector. Publishing the same signature in two places does not change this.

### Verification of the variants

The `mirror-oss` job already verifies that the mirrored `update.json` reports the tag version and that every mirrored object answers HTTP 200; it additionally verifies that the mirrored manifest's installer URL is on the OSS host. The `release` job's upload plus the documented final-release verification cover the GitHub variant (installer URL on `github.com`, same version and signature). The variants must not be swapped between hosts; the release procedure's checklist is updated accordingly.

## Risks / Trade-offs

- [A 200 response with a non-JSON body aborts the endpoint chain] → crate behavior (`res.json()?` returns early, skipping remaining endpoints); network-level failures and non-success statuses do fall through. Accepted: captive-portal/hijack pages impersonating these two hosts are rare, and the failure still lands in the existing manual-download fallback.
- [Manifest variants drifting apart (version or signature mismatch)] → both variants are generated in one step from the same `.sig` file and version; `mirror-oss` and the release checklist verify version/host/signature equality.
- [Overseas clients pull a large installer cross-border from OSS in the common case] → slower than GitHub for some users but functional; they keep the GitHub path when OSS is unreachable. Revisit with a latency probe only if reported as a real problem.
- [Existing v0.2.3 clients keep the single OSS URL] → their behavior is unchanged by this change; the fallback reaches them with the next release they install (manually if needed, as documented for the affected machine).

## Migration Plan

Land the client endpoint list and the workflow variant generation together; both are inert until the next `v*` tag. Old clients ignore the extra variant; new clients ignore the single-URL layout. Rollback is reverting the endpoint constant to a single URL — either manifest layout remains consumable.

## Open Questions

None — endpoint order (OSS first) was confirmed by the maintainer.
